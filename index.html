The Folk Extension Algebra: A Formal Semantics of
Compositional File Extensions for Reactive Tangible Computing

Or: why .svg.folk and .folk.svg are not the same file
cwervo
Folk Computer Playground · Independent
Draft preprint. In the spirit of OOPSLA (Onward! track). Not a real arXiv submission.

Abstract

Folk Computer programs live as physical pages sensed by cameras and evaluated as a shared database of statements. As such programs began to emit and embed other notations — SVG for vector output, HTML/CSS/JS for panels, Tcl for raw escape, and even BNF for self-description — an informal convention of stacked file extensions emerged in practice (e.g. .tcl.html.folk). This paper argues that these stacks are not decoration: they are a lightweight typing discipline that names, for each file, the exact nesting of language runtimes that own its brackets. We give a formal account. We define the Folk Extension Algebra, in which a dotted extension chain read right-to-left denotes a host stack from outermost runtime to innermost guest, and prove informally that hosting is non-commutative: swapping two extensions swaps which parser is authoritative. We present a single BNF metagrammar, a core grammar for Folk, and a higher-order host combinator that, instantiated eleven times, yields concrete grammars for .bnf.folk, .svg.folk, .folk.svg, .tcl.folk, .folk.tcl, .html.folk, .tcl.html.folk, .css.folk, .folk.css, .js.folk, and .folk.js. We close with the semantics of reflection between host and guest layers, using Folk's statement database as a universal interchange, and relate the design to #lang, literate programming, MIME suffix trees, and polyglot files.

Keywords: file extensions, host languages, embedded DSLs, tangible computing, Folk, reactive systems, grammar composition, projectional syntax

1. Introduction

A Folk Computer program is a piece of paper. A projector-and-camera table watches the page, optically recognizes it, and runs the text printed on it as a set of reactive statements against a shared, table-wide database [1]. The canonical file extension for such a page is .folk. In day-to-day use, however, a single .folk extension quickly stops being enough to describe what is actually on the page.

Consider three real situations. A page that draws vector graphics is, in every meaningful sense, an SVG generator that happens to be written as Folk. A page that renders a live web panel is an HTML document whose text is Tcl-templated and which is, in turn, produced by Folk. And an ordinary .svg illustration might want to sprout a little reactive behavior — a few Folk rules embedded directly inside the drawing. Practitioners already reach for stacked extensions to name these: drawing.svg.folk, panel.tcl.html.folk, badge.folk.svg. The convention appears in the wild the moment a workflow needs to round-trip a Folk page through another tool.1

The thesis of this paper is simple: the order of stacked extensions is meaningful, and it denotes a stack of language runtimes. Reading the chain right-to-left gives the host order — the outermost runtime first, each language to the left hosted by the one to its right, down to the innermost guest that carries the file's "real" content. Under this reading .svg.folk (a Folk program that emits SVG) and .folk.svg (an SVG document that embeds Folk) are genuinely different file types with different top-level parsers, different loaders, and different failure modes. The extension chain is a type, and like most types it is not commutative.

We make this precise. Section 2 recalls just enough of Folk. Section 3 defines the extension algebra and its central duality. Sections 4–6 give a metanotation, a core grammar for Folk, and a single higher-order host combinator. Section 7 instantiates that combinator eleven times, once per file type in the title. Section 8 gives the reflective semantics that make the whole thing hang together, and Section 9 situates it among related ideas.

2. Background: Folk in One Page

Folk is hosted on Tcl. A program is a sequence of statements, plus ordinary Tcl. The core verbs are:

Wish $this is outlined thick white
Wish $this is titled "Key monitor"

When keyboard /k/ claims key /key/ is down with timestamp /any/ {
  Wish $this is labelled "$k | $key | $any"
}

Claim the sky is blue
Commit c { Claim $this has seen 0 boops }

Four ideas matter for what follows. (i) Claims and Wishes assert facts and desires into the database. (ii) When is a reactive pattern-matched rule; its body re-runs whenever matching statements exist. (iii) Pattern variables are written /name/ and capture matched terms. (iv) Escapes to Tcl are pervasive: $var substitutes a value and [script] evaluates Tcl inline. The last point is the crux for composition — Folk statement payloads are strings, and strings can carry any other notation, with $ and […] serving as interpolation holes into the guest text.

Observation 2.1 (Folk is already a two-level language). Because every Folk file is also a Tcl script, .folk is silently .tcl.folk with the Tcl left implicit. The extension algebra below simply makes such implicit hosts nameable, and lets us stack more of them.

3. The Extension Algebra

Fix a finite alphabet of extension symbols Σ = { folk, tcl, svg, html, css, js, bnf }. A filename is a stem followed by a non-empty dotted extension chain drawn from Σ.

Definition 3.1 (Host order). For a chain en·…·e1·e0 (written left-to-right as it appears in the filename, so e0 is rightmost), the host relation ⊊ is
e0 ⊊ e1 ⊊ … ⊊ en
read "e0 hosts e1 hosts …". The rightmost symbol e0 is the top host (the runtime the loader dispatches on); the leftmost symbol en is the innermost guest (the file's effective content type). Each ek is embedded in, templated by, or emitted from ek+1.

Two mnemonics fall out, and they point in opposite directions. Control flows right-to-left: the top host loads first and delegates inward. Content flows left-to-right: the innermost guest is the payload, lifted outward through each host until the top host runs it. The rightmost extension answers "who parses the outermost brackets?"; the leftmost answers "what is this file really about?"

Principle 3.2 (Non-commutativity of hosting). In general a·b ≠ b·a as file types. The chains name different top hosts, so a conforming loader runs a different parser first, and a syntactically valid a·b file is typically not a valid b·a file. Concatenation of chains is associative (nesting is), giving a monoid on Σ+ under juxtaposition, but the hosting interpretation of that monoid is order-sensitive.

This yields the paper's organizing distinction. Every file type below is either Folk-as-host (folk is rightmost — Folk owns the outer brackets and emits the guest) or Folk-as-guest (folk is not rightmost — some other runtime owns the outer brackets and embeds Folk). The two families are duals, and the marquee pairs .svg.folk/.folk.svg, .tcl.folk/.folk.tcl, and the CSS/JS analogues, exhibit the duality directly.

ChainTop host (loader)Innermost guestFamily
bnf.folkFolkBNFFolk-as-host / emit
svg.folkFolkSVGFolk-as-host / emit
folk.svgSVGFolkFolk-as-guest / embed
tcl.folkFolkTclFolk-as-host / emit
folk.tclTcl (tclsh)FolkFolk-as-guest / embed
html.folkFolkHTMLFolk-as-host / emit

4. Metanotation

All grammars use one EBNF-flavored metanotation. Nonterminals are ⟨angled⟩ and blue; terminal keywords are bold-ish gold; guest text is set literally. Operators:

⟨x⟩            nonterminal
"lit"          terminal (literal characters)
a | b          alternation
{ a }          zero or more repetitions
{ a }+         one or more repetitions
[ a ]          optional
( a )          grouping
⟨G⟩            grammar parameter (a nonterminal supplied as an argument)
Host⟨G⟩       higher-order production, instantiated per guest G
// text        metagrammar comment

5. Core Folk Grammar

We first give the grammar of Folk itself, ⟨folk⟩, reused throughout. Lexically, Folk is Tcl: words are whitespace-separated, braces group, brackets substitute.

5.1  Lexical layer

⟨word⟩        ::= ⟨bareword⟩ | ⟨string⟩ | ⟨brace-group⟩
                  | ⟨var⟩ | ⟨subst⟩ | ⟨pattern-var⟩
⟨bareword⟩    ::= { ⟨wchar⟩ }+                // any non-space, non-metacharacter run
⟨var⟩         ::= "$" ⟨name⟩ | "${" ⟨name⟩ "}"
⟨subst⟩       ::= "[" ⟨tcl-script⟩ "]"       // inline Tcl evaluation
⟨pattern-var⟩ ::= "/" ⟨name⟩ "/"           // capture / wildcard
⟨string⟩      ::= '"' { ⟨schar⟩ | ⟨var⟩ | ⟨subst⟩ } '"'
⟨brace-group⟩ ::= "{" { ⟨any⟩ } "}"          // literal, unsubstituted
⟨name⟩        ::= { ⟨alpha⟩ | ⟨digit⟩ | "_" | "::" }+

5.2  Statement layer

⟨folk⟩        ::= { ⟨stmt⟩ | ⟨tcl-stmt⟩ | ⟨comment⟩ }
⟨stmt⟩        ::= ⟨claim⟩ | ⟨wish⟩ | ⟨when⟩
                  | ⟨every⟩ | ⟨commit⟩ | ⟨hold⟩
⟨claim⟩       ::= "Claim" ⟨phrase⟩
⟨wish⟩        ::= "Wish" ⟨phrase⟩
⟨when⟩        ::= "When" ⟨cond⟩ { "&" ⟨cond⟩ } ⟨block⟩
⟨every⟩       ::= "Every" "time" ⟨cond⟩ { "&" ⟨cond⟩ } ⟨block⟩
⟨commit⟩      ::= "Commit" [ ⟨name⟩ ] ⟨block⟩
⟨hold⟩        ::= "Hold" [ ⟨name⟩ ] ⟨block⟩
⟨cond⟩        ::= ⟨phrase⟩
                  | "the collected matches for" ⟨list⟩ "are" ⟨pattern-var⟩
⟨block⟩       ::= "{" ⟨folk⟩ "}"          // recursive: bodies contain statements
⟨phrase⟩      ::= { ⟨word⟩ }+
⟨comment⟩     ::= "#" { ⟨any⟩ } ⟨newline⟩
⟨tcl-stmt⟩    ::= ⟨word⟩ { ⟨word⟩ }       // proc, fn, set, if, foreach, expr, ...

The key composition hook is ⟨string⟩ and ⟨brace-group⟩: any guest language rides inside them, with ⟨var⟩ and ⟨subst⟩ punching interpolation holes into the guest. This is what the next section abstracts.

6. The Host Combinator

Rather than write eleven bespoke grammars, we define two higher-order productions parameterized by a guest grammar ⟨G⟩. Emit covers Folk-as-host (Folk brackets outside, guest text inside payloads). Host covers Folk-as-guest (a guest document outside, Folk statements inside guest-native carriers).

6.1  Emit⟨G⟩ — Folk hosts, and emits, G

Emit⟨G⟩      ::= { ⟨stmt⟩ | ⟨tcl-stmt⟩ | ⟨comment⟩
                  | ⟨g-emitting-stmt⟩ }
⟨g-emitting-stmt⟩
              ::= ( "Wish" | "Claim" ) ⟨phrase⟩ ⟨G-payload⟩ { ⟨phrase⟩ }
⟨G-payload⟩   ::= '"' ⟨G-frag⟩ '"' | "{" ⟨G-frag⟩ "}"
⟨G-frag⟩      ::= { ⟨G⟩ | ⟨var⟩ | ⟨subst⟩ }   // guest G with Folk holes

Intuition: ⟨G-frag⟩ is the guest grammar ⟨G⟩ with two extra productions, ⟨var⟩ and ⟨subst⟩, admitted anywhere a guest token may appear. The guest is thus a template over Folk values, and the Folk runtime is the emitter.

6.2  Host⟨G⟩ — G hosts, and embeds, Folk

Host⟨G⟩      ::= { ⟨G⟩ | ⟨folk-region⟩G }
⟨folk-region⟩G
              ::= ⟨carrier-open⟩G ⟨folk⟩ ⟨carrier-close⟩G

The carrier is guest-native syntax that the guest parser already tolerates as an opaque region — a processing instruction, an at-rule, a tagged template, a comment fence, or a custom command. The guest owns the outer brackets; Folk text is lifted out of the carriers, evaluated, and its results reflected back (Section 8). Carriers per guest:

Guest Gcarrier-opencarrier-close
SVG / XML<?folk?>  (or <folk:when>…</folk:when>)
CSS@folk {}
JSfolk`  (tagged template)`  (or /*<folk>*/ … /*</folk>*/)
Tclfolk {}

7. The Eleven Schemas

Each file type is now a one-line instantiation of Section 6, plus (where needed) the guest grammar it references. We give the instantiations grouped by family, and expand the guest grammars that are not standard off-the-shelf notations.

7.1  Folk-as-host (emit family)

7.1.1  .bnf.folk — a Folk program that emits grammar

The self-referential base case: a Folk page whose payloads are BNF productions. This very document's grammar of grammars is, fittingly, a .bnf.folk.

⟨.bnf.folk⟩  ::= Emit⟨⟨bnf⟩⟩
⟨bnf⟩         ::= { ⟨production⟩ }
⟨production⟩  ::= ⟨nonterminal⟩ "::=" ⟨rhs⟩
⟨rhs⟩         ::= ⟨alt⟩ { "|" ⟨alt⟩ }
⟨alt⟩         ::= { ⟨nonterminal⟩ | ⟨terminal⟩ }+
# badge.bnf.folk — Folk emits (and can typeset) a grammar
Claim production "⟨greeting⟩ ::= \"hello\" ⟨name⟩"
When /p/ is a production {
  Wish $this draws text "$p" with anchor left
}

7.1.2  .svg.folk — a Folk program that emits SVG

⟨.svg.folk⟩  ::= Emit⟨⟨svg⟩⟩       // ⟨svg⟩ = standard SVG element grammar
When the clock time is /t/ {
  Wish $this draws svg "<circle r='[expr {60+40*sin($t)}]' fill='tomato'/>"
}

7.1.3  .html.folk — a Folk program that emits HTML

⟨.html.folk⟩ ::= Emit⟨⟨html⟩⟩

7.1.4  .tcl.html.folk — depth-3: Folk emits HTML that templates Tcl

The showcase case. The guest of Folk is not plain HTML but Tcl-in-HTML: an HTML document whose text nodes and attribute values may contain Tcl template holes. We express this by nesting the combinator — the guest grammar handed to Emit is itself an Emit-style template.

⟨.tcl.html.folk⟩
               ::= Emit⟨ ⟨html-with-tcl⟩ ⟩
⟨html-with-tcl⟩
               ::= { ⟨html-node⟩ | ⟨tcl-hole⟩ }
⟨tcl-hole⟩    ::= "[[ " ⟨tcl-script⟩ " ]]"    // inner (HTML-level) template
                 | ⟨var⟩ | ⟨subst⟩          // outer (Folk-level) holes

Note the two distinct template layers: $x/[…] are resolved by Folk at emit time (outer), while [[ … ]] survives into the HTML to be resolved by an HTML-side Tcl templater at render time (inner). Reading depth off the extension chain — three symbols, three layers — is exactly the payoff of Definition 3.1.

7.1.5  .css.folk — a Folk program that emits CSS

⟨.css.folk⟩  ::= Emit⟨⟨css⟩⟩

7.1.6  .js.folk — a Folk program that emits JS

⟨.js.folk⟩   ::= Emit⟨⟨js⟩⟩

7.1.7  .tcl.folk — a Folk program that is Tcl-forward

The near-degenerate emit case (cf. Observation 2.1). Because Folk's body already is Tcl, Emit⟨tcl⟩ collapses into ordinary Folk; the left tcl is a documentation marker declaring "this page is mostly bare Tcl procedures with a few statements," and asks tooling to lint it as Tcl.

⟨.tcl.folk⟩  ::= Emit⟨⟨tcl⟩⟩  ≡  ⟨folk⟩   // with Tcl-forward lint intent

7.2  Folk-as-guest (embed family)

Here the top host is some other runtime; Folk is embedded in carriers and never sees the outer brackets. Each is one line of Host⟨G⟩.

7.2.1  .folk.svg — an SVG document embedding Folk

⟨.folk.svg⟩  ::= Host⟨⟨svg⟩⟩
                     // carrier: <?folk … ?>  or  <folk:when>…</folk:when>
<svg xmlns="http://www.w3.org/2000/svg"
     xmlns:folk="https://folk.computer/ns">
  <circle id="dot" r="20" fill="gray"/>
  <?folk
    When the clock time is /t/ {
      Wish #dot has fill "hsl([expr {$t*40}] 80% 60%)"
    }
  ?>
</svg>

7.2.2  .folk.tcl — a Tcl script embedding Folk

Runs under bare tclsh, not the Folk runtime. A folk { … } command reflects the enclosed statements into a local database — useful for headless tests and for driving Folk from ordinary Tcl automation.

⟨.folk.tcl⟩  ::= Host⟨⟨tcl⟩⟩      // carrier: folk { … }
#!/usr/bin/env tclsh
package require folk
set db [folk::db new]
folk {
  Claim the sky is blue
  When the sky is /color/ { puts "sky: $color" }
}
$db step

7.2.3  .folk.css — a stylesheet embedding Folk

⟨.folk.css⟩  ::= Host⟨⟨css⟩⟩      // carrier: @folk { … }
.panel { color: white; }
@folk {
  When $this has brightness /b/ {
    Wish .panel has background "rgb($b $b $b)"
  }
}

7.2.4  .folk.js — a module embedding Folk

⟨.folk.js⟩   ::= Host⟨⟨js⟩⟩
                     // carrier: folk`…`  or  /*<folk>*/ … /*</folk>*/
import { folk } from "folk";
export const rule = folk`
  When /p/ has position /xy/ {
    Wish /p/ is outlined green
  }
`;
Duality, restated. The pairs collapse to a single equation: for any web guest G ∈ {svg, css, js, tcl}, .G.folk = Emit⟨G⟩ and .folk.G = Host⟨G⟩. Same two languages; the extension order alone selects emitter vs. embedder.

8. Reflective Semantics

What makes both families interoperate is that Folk's runtime value is not a string but a set of statements. We sketch the two directions.

Emit (reification). For Emit⟨G⟩, evaluation of the Folk program yields Wishes whose payloads are guest fragments. A collector concatenates the satisfied fragments in document order and hands the result to G's own consumer (a browser, an SVG rasterizer, a Tcl source). Folk holes $x/[…] are resolved before hand-off; inner holes (as in .tcl.html.folk) are preserved verbatim and resolved by the guest's own templater afterward. Emit is thus staged: one stage per host level, outermost first.

Host (reflection). For Host⟨G⟩, the guest parser runs first and produces a document tree with opaque carrier nodes. A pre-pass extracts each ⟨folk-region⟩, evaluates it against the table database, and reflects the results back onto guest nodes addressed by selector (#id, class, XPath). The guest is authoritative for structure; Folk supplies behavior. Crucially the same database is shared across all regions and, on a live table, across all pages — so a .folk.css rule and a .svg.folk page can communicate through Claims without either knowing the other's file type.

Principle 8.1 (Brackets ownership). At every level exactly one language owns the outermost brackets and is responsible for delimiting the next level's regions. The extension chain is a total order on bracket ownership; a well-formed file is one whose actual delimiters agree with that order. Most "polyglot" bugs are a disagreement between the chain and the bytes.

An immediate corollary is a typing rule for pipelines: a tool that consumes X and produces Y transforms a file's chain by popping X from one end and pushing Y; the chain is a running record of every runtime the bytes have passed through, which is why the temporary artifacts observed in practice (e.g. program.folk.temp) already stack extensions without anyone deciding they should.

9. Related Work

Language-oriented programming. Racket's #lang line selects a reader/expander per file [2]; our chain generalizes the idea to a stack of readers named positionally rather than a single in-band directive. Literate programming [3] interleaves two languages (prose and code) with tangling/weaving as our Emit/Host duals. MIME & media-type suffixes (application/soap+xml) already read structured-syntax suffixes right-to-left, the same direction as Definition 3.1; we differ by treating each level as an executable host, not merely a serialization. Polyglot files and projectional editors (JetBrains MPS) motivate Principle 8.1: keep exactly one authoritative parser per level. Server-page templating (JSP/ERB/PHP) is the classical two-level emit case that .tcl.html.folk extends to three. Against all of these, Folk's contribution is the shared statement database as the interchange between layers, and the observation that a filesystem-visible extension chain suffices to name the whole tower.

10. Conclusion

Stacked extensions on Folk files were never noise. Read right-to-left they name a stack of hosting runtimes; the rightmost owns the outer brackets, the leftmost is the payload, and swapping any two changes the file's type because hosting does not commute. A single host combinator, instantiated eleven times, formalizes every case in the title, unifying the emit and embed families as duals over a shared reflective database. The practical upshot is modest and usable today: name your files by their host order, keep one parser per level, and let the extension chain carry the type. .svg.folk draws; .folk.svg comes alive. They are not the same file, and now we can say exactly why.
